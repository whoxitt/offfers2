# OfferBot

Существующий Telegram Business-бот на aiogram 3 и PostgreSQL. Проект дорабатывается поверх прежней структуры; SQLite не используется.

## Команда офера

Используется только префикс `Оф` (регистр не важен):

`Оф https://t.me/nft/PartySparkler-140864 150 stars`

Язык можно указать в конце команды: `англ/en`, `араб`, `кидай` (китайский). Валюта: `stars`, `gram` или рубли. Получатель для кнопки передачи настраивается командой `/transfer @username`.

Срок нового офера — 24 часа. Ожидающие оферы по истечении срока переводятся в `expired`, а не удаляются.

## Стартовое меню и баннер

`/start` показывает фото (если администратор загрузил его через админку) с подписью «Привет, выбери действие» и кнопками «Купить», «Инструкция», «Я чайник». Фото хранится как Telegram `file_id` в существующей таблице PostgreSQL `offer_settings`; после перезапуска оно сохраняется.

Чтобы изменить фото: `/admin` → «Изменить баннер» → отправить фото обычным сообщением. Для отмены отправьте `/cancel`.

## Настройка и запуск

1. Установите Python 3.10+.
2. Установите зависимости: `pip install -r requirements.txt`.
3. Создайте `.env` по образцу `.env.example` либо задайте те же переменные на сервере.
4. Обязательно задайте `BOT_TOKEN`, `OWNER_ID`, `DATABASE_URL` (существующая PostgreSQL) и действующие платёжные переменные, если используется оплата.
5. Запуск: `python bot.py`.

Не добавляйте `.env` в архивы, Git или публичные репозитории.

## Проверки

```bash
python -m py_compile bot.py config.py database.py offer.py payment.py
```

Проверка отправки Business-сообщений, видимости клавиатуры на реальном клиенте, оплаты в TON и сохранности существующей БД требует подключения к реальному Telegram-боту и тестовой/рабочей PostgreSQL. Одного локального `py_compile` для этого недостаточно.


## TON-доступ (обновлённая система)

Платёжная цена задаётся в TON через `PAYMENT_PRICE` (по умолчанию 5), срок — через
`ACCESS_DURATION_HOURS` (по умолчанию 48). `TON_WALLET` — адрес кошелька-получателя,
`TON_API_KEY` — отдельный ключ авторизации TonAPI. API-ключ не является кошельком.

Скопируйте `.env.example` в `.env` локально и заполните `BOT_TOKEN`, `OWNER_ID`,
`DATABASE_URL` и `TON_API_KEY`. Не добавляйте `.env` в архив или Git.

При первом запуске новая схема и дополнительные поля PostgreSQL создаются
без удаления существующих таблиц: `access_subscriptions`, `access_links`,
`access_link_requests`, а также `payments.tx_hash`. Отдельную команду миграции
выполнять не требуется: `Database.init_schema()` применяет идемпотентные DDL
при старте. Перед обновлением Railway всё равно рекомендуется сделать backup PostgreSQL.

Администратор (`OWNER_ID`) имеет безусловный доступ. Команды владельца:
- `/grant ID ЧАСЫ` — временная выдача (например, `/grant 123456 48`);
- `/grantforever ID` — бессрочный доступ;
- `/revoke ID` — отзыв доступа и привязанных аккаунтов;
- `/accesslist` — список активных подписок.

Проверка TON выполняется только по кнопке «Проверить оплату». Транзакция должна
иметь входящее сообщение на настроенный кошелёк, точную сумму не меньше цены,
точный комментарий платежа и hash; hash хранится с уникальным ограничением.
Если TonAPI недоступен, доступ не выдаётся.

Привязка дополнительного аккаунта: второй аккаунт вводит username основного,
после чего владелец основного аккаунта должен подтвердить запрос в Telegram.
У всех связанных аккаунтов общий срок подписки.

### Совместимость со старыми записями доступа

В старой схеме одна таблица использовалась и для ручных выдач, и для успешных платежей,
поэтому достоверно восстановить срок старой платной подписки нельзя. Старые записи
без истории оплаченного платежа сохраняются как прежние административные выдачи.
Если у пользователя есть старый оплаченный платёж, но нет новой записи срока,
доступ автоматически не продлевается и не получает новые 48 часов: требуется
ручная проверка и выдача через `/grant` или `/grantforever`. Если один и тот же
аккаунт одновременно получал ручной доступ и платил, источник старой выдачи
невозможно различить по прежней схеме.
